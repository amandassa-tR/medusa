Medusa Testing

[/raw]
Medusa is a free, open-source, headless commerce platform for building ecommerce stores, marketplaces, and other digital commerce applications. It ships commerce modules (products, carts, orders, payments, promotions, customers, and more) plus tools to customize them without reinventing core commerce logic. The Medusa application used in this project is the DTC starter: a production-ready monorepo with a Medusa backend and a Next.js storefront. Typical local URLs are:
  • Storefront: http://localhost:8000
  • Admin dashboard: http://localhost:9000/app
  • Backend API: http://localhost:9000
Medusa is built on Node.js and TypeScript. The server is Express-based, PostgreSQL is the datastore, and clients (storefront, admin, custom apps) talk to Medusa through HTTP API routes. A request typically flows through four layers:
  1. API routes (HTTP entry point)
  2. Workflows (opinionated business logic)
  3. Modules (domain services and data models)
  4. PostgreSQL (and optional Redis, file storage, and other infrastructure)
You can customize the following in a Medusa project:
  • Commerce modules and custom modules
  • Workflows, API routes, subscribers, and scheduled jobs
  • The Medusa Admin (widgets, routes, and UI extensions)
  • The Next.js storefront (catalog, cart, checkout, customer accounts)
  • Plugins and third-party integrations (payments, fulfillment, CMS, ERP)
A default catalog, checkout, customer accounts, and admin dashboard are included in the starter. Further customizations live under apps/backend/src (API routes, modules, workflows, admin) and apps/storefront (storefront UI). According to the testing pyramid, you can test your Medusa application through
  • Unit testing
  • Integration testing
  • End-to-end testing

Unit Testing

As a project grows, it becomes difficult to keep track of every method and class. Through unit testing, you can ensure that individual units of code work as expected, without starting the full Medusa server or talking to a real database. Medusa's Testing Framework (@medusajs/test-utils) is built for integration tests. Unit tests are written with Jest. The DTC backend already includes the scripts and Jest config for this. Place unit tests next to the code they cover, under a __tests__ folder, using the *.unit.spec.ts suffix. For example, if the function lives in src/utils/is-email.ts, the unit test belongs in src/utils/__tests__/is-email.unit.spec.ts. The backend jest.config.js selects those files when TEST_TYPE=unit: 
if (process.env.TEST_TYPE === "integration:http") {
  module.exports.testMatch = ["**/integration-tests/http/*.spec.[jt]s"];
} else if (process.env.TEST_TYPE === "integration:modules") {
  module.exports.testMatch = ["**/src/modules/*/__tests__/**/*.[jt]s"];
} else if (process.env.TEST_TYPE === "unit") {
  module.exports.testMatch = ["**/src/**/__tests__/**/*.unit.spec.[jt]s"];
}
A typical Jest unit test looks like this (from Medusa's own utilities):
import { validateEmail } from "../is-email"

describe("validateEmail", () => {
  it("successfully validates an email", () => {
    expect(validateEmail("test@email.com")).toBe("test@email.com")
    expect(validateEmail("test.test@email.com")).toBe("test.test@email.com")
  })

  it("throws on an invalid email", () => {
    expect.assertions(1)

    try {
      validateEmail("not-an-email")
    } catch (e) {
      expect(e.message).toBe("The email is not valid")
    }
  })
})
The example above uses Jest assertions to validate both the success path and the error path. Below is another unit test that checks several inputs with a table of expectations:
import { toCamelCase } from "../to-camel-case"

describe("toCamelCase", function () {
  it("should convert all cases to camel case", function () {
    const expectations = [
      { input: "testing-camelize", output: "testingCamelize" },
      { input: "this_is-A-test", output: "thisIsATest" },
      { input: "testingAlreadyCamelized", output: "testingAlreadyCamelized" },
    ]

    expectations.forEach((expectation) => {
      expect(toCamelCase(expectation.input)).toEqual(expectation.output)
    })
  })
})

Ways to Execute Medusa Unit Tests

Medusa unit tests can be executed in the following ways.
  • Command Line Interface (CLI) From apps/backend, run all unit tests, or pass a path to run a subset: 
    pnpm test:unit
pnpm test:unit src/utils/__tests__/is-email.unit.spec.ts
    The test:unit script is: 
    TEST_TYPE=unit NODE_OPTIONS=--experimental-vm-modules jest --silent --runInBand --forceExit
  • IDE (VS Code, WebStorm, and similar) You can run Jest from the editor. Configure the IDE to use the same jest.config.js and set TEST_TYPE=unit so it picks up *.unit.spec.ts files. You can run the whole suite or a single test, the same as from the CLI.

Frontend and JavaScript Unit Tests

The Medusa Admin and design system are React/TypeScript. Packages such as @medusajs/ui and the admin Vite plugin use Vitest for component and package unit tests (vitest --run). The Next.js storefront in the DTC starter does not ship a first-party unit-test runner of its own; storefront behavior is covered by integration tests on the API and by end-to-end tests on the UI.

Integration Testing

The next step after testing units in isolation is to see if they work together. This is where integration testing comes in. In Medusa, that means API routes, workflows, modules, the database, and third-party services (payment, fulfillment, file storage, and so on). Medusa provides @medusajs/test-utils for this layer. Install it as a devDependency, configure Jest, and add the three test scripts already present in the DTC backend: 
"test:integration:http": "TEST_TYPE=integration:http NODE_OPTIONS=--experimental-vm-modules jest --silent=false --runInBand --forceExit",
"test:integration:modules": "TEST_TYPE=integration:modules NODE_OPTIONS=--experimental-vm-modules jest --silent=false --runInBand --forceExit",
"test:unit": "TEST_TYPE=unit NODE_OPTIONS=--experimental-vm-modules jest --silent --runInBand --forceExit"
The main types you will want to cover:
  1. HTTP tests for API routes (store and admin)
  2. Workflow tests for multi-step business logic
  3. Module tests for a module's main service and data models
  4. Third-party integration tests (payment providers, fulfillment, CMS, ERP)
medusaIntegrationTestRunner starts a full Medusa application, creates a temporary PostgreSQL database, runs your Jest tests, then drops that database. Increase the Jest timeout because these tests talk to the database: 
jest.setTimeout(60 * 1000)
Below is an HTTP integration test for a custom GET route at /custom:
import { medusaIntegrationTestRunner } from "@medusajs/test-utils"

medusaIntegrationTestRunner({
  testSuite: ({ api, getContainer }) => {
    describe("Custom endpoints", () => {
      describe("GET /custom", () => {
        it("returns correct message", async () => {
          const response = await api.get(`/custom`)

          expect(response.status).toEqual(200)
          expect(response.data).toHaveProperty("message")
          expect(response.data.message).toEqual("Hello, World!")
        })
      })
    })
  },
})

jest.setTimeout(60 * 1000)
Store routes need a publishable API key. Create one in beforeAll and pass it on the request:
const response = await api.get(`/store/custom`, {
  headers: {
    "x-publishable-api-key": pak.token,
  },
})
Workflows are tested with the same runner. Execute the workflow against the test container and assert the result:
import { medusaIntegrationTestRunner } from "@medusajs/test-utils"
import { helloWorldWorkflow } from "../../src/workflows/hello-world"

medusaIntegrationTestRunner({
  testSuite: ({ getContainer }) => {
    describe("Test hello-world workflow", () => {
      it("returns message", async () => {
        const { result } = await helloWorldWorkflow(getContainer()).run()

        expect(result).toEqual("Hello, World!")
      })
    })
  },
})

jest.setTimeout(60 * 1000)
Module integration tests use moduleIntegrationTestRunner. They run a test Medusa application with only the specified module enabled:
import { moduleIntegrationTestRunner } from "@medusajs/test-utils"
import { BLOG_MODULE } from ".."
import BlogModuleService from "../service"
import Post from "../models/post"

moduleIntegrationTestRunner<BlogModuleService>({
  moduleName: BLOG_MODULE,
  moduleModels: [Post],
  resolve: "./src/modules/blog",
  testSuite: ({ service }) => {
    describe("BlogModuleService", () => {
      it("says hello world", () => {
        const message = service.getMessage()
        expect(message).toEqual("Hello, World!")
      })
    })
  },
})

jest.setTimeout(60 * 1000)
Run HTTP and workflow tests from apps/backend with: 
pnpm test:integration:http
Run module tests with: 
pnpm test:integration:modules
Medusa's own CI pipeline shards unit tests and HTTP/package integration tests on GitHub Actions, with PostgreSQL and Redis services. That is the right place for this layer. Browser-level flows belong in end-to-end tests.

End-to-End Testing

End-to-end or system testing verifies the behavior of the application from start to finish, covering the entire business process. This type of testing is also known as "black-box testing," as it focuses on functionality without requiring knowledge of the internal workings of the system. The goal is to simulate real-world scenarios and catch issues that appear only when a shopper uses the storefront, a merchant uses the admin, or both apps work together (for example, a merchant creates a promotion and a shopper redeems it at checkout). You can do that using the following ways.
  • UI testing with browser automation tools
  • Selenium-based tools
  • testRigor
Medusa does not ship a Magento-style functional testing framework (MFTF) or a first-party Playwright suite. Official tooling stops at Jest plus @medusajs/test-utils. Browser coverage for the DTC storefront and admin is handled with testRigor in this project. We won't get into Selenium-based testing here since it might not be the most optimal way to use for end-to-end testing due to its limitations.

UI testing with supported tools

Teams sometimes add Playwright (or similar) against the Next.js storefront. That requires selectors, waits, and a local browser driver, and those tests tend to break when the storefront markup changes. For the Medusa testing project, end-to-end coverage is written in plain English with testRigor instead, including flows that start in the admin at localhost:9000/app and finish on the storefront at localhost:8000.

Critical Test Cases Included
The pre-built suite includes these essential Medusa workflows that every commerce site must have working perfectly:
1. Guest Checkout (Complete Purchase Flow)
Test: Browse Shirts, configure Medusa T-Shirt (S / White), add to cart, check out as a guest, and confirm the order. Why it's critical: This is the money-making flow. Setting Up GitHub CI/CD Integration

For automated testing in your GitHub repository, you'll need to configure your testRigor credentials as GitHub secrets. This approach differs from local testing by using GitHub's secure environment variables instead of a local .env file. Medusa's own pipeline already runs sharded unit tests and HTTP/package integration tests. Add testRigor as the end-to-end job on top of that, pointed at a running storefront (or start the DTC stack in the workflow).

Step 1: Add GitHub Secrets

  1. Go to your GitHub repository
  2. Click on "Settings" → "Secrets and variables" → "Actions"
  3. Add the following:
    • As a secret:
      • MEDUSA_AUTH_TOKEN: Your testRigor auth token (keep this private)
    • As variables:
      • MEDUSA_TEST_SUITE_ID: Your testRigor Test Suite ID
      • MEDUSA_BASE_URL: Your Medusa storefront URL
For further information on creating secrets and variables in GitHub Actions, you can check the official GitHub documentation on secrets and variables.
Required GitHub Secrets and Variables:
  • MEDUSA_TEST_SUITE_ID: Your testRigor Test Suite ID (e.g., 12345)
  • MEDUSA_AUTH_TOKEN: Your testRigor auth token (format: ########-####-####-####-############)
  • MEDUSA_BASE_URL: Your Medusa storefront URL (e.g., https://yourstore.com or http://localhost:8000)

Step 2: Use in GitHub Actions

In your GitHub Actions workflow file, reference these secrets like this: 
- name: Run testRigor Tests
  run: |
    npm install -g @testrigor/testrigor-cli
    testrigor test-suite run ${{ vars.MEDUSA_TEST_SUITE_ID }} --token ${{ secrets.MEDUSA_AUTH_TOKEN }} --url ${{ vars.MEDUSA_BASE_URL }} --test-cases-path medusa/testRigor/testcases
  env:
    MEDUSA_AUTH_TOKEN: ${{ secrets.MEDUSA_AUTH_TOKEN }}
    MEDUSA_TEST_SUITE_ID: ${{ vars.MEDUSA_TEST_SUITE_ID }}
    MEDUSA_BASE_URL: ${{ vars.MEDUSA_BASE_URL }}
If the workflow starts the DTC stack on the runner, add --localhost so testRigor can reach http://localhost:8000 and http://localhost:9000. Cross-app cases that open url "http://localhost:9000/app" need the backend up as well. You can further integrate this workflow with your own instance of Medusa to make your commerce platform completely set up for CI/CD. Key Difference: While local testing uses a .env file, CI/CD uses GitHub's secure secret management system, ensuring your credentials are encrypted and only accessible to authorized workflows.

Troubleshooting Tips

If you find any issues:
  • Make sure the Medusa storefront and backend are running and accessible at the URLs you specified (http://localhost:8000 and http://localhost:9000/app for local)
  • Check your .env file — ensure all three values are correct and there are no extra spaces
  • Verify the admin user — merchant tests log in as admin@test.com / supersecret unless you changed the starter user
  • Match the region — guest checkout in this project uses Denmark, postal code 2100, Copenhagen, Standard Shipping, and Manual Payment
  • Verify your testRigor account — make sure you can log in and see the test suite
  • Check your internet connection — testRigor needs to reach the cloud (and to download the CLI on first run)
If a local tunnel run fails to see the admin app, confirm both pnpm dev processes are up and that --localhost is passed to the CLI.
